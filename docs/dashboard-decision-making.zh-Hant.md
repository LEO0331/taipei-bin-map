# 從公共設施資料到可行動的城市服務洞察

## 定位與問題背景

這個儀表板的核心不是「把地點畫在地圖上」，而是把分散、格式不一且品質不同的公開資料，轉換成民眾、服務人員與規劃者都能理解的查詢介面。使用者可依設施類型、行政區、文字條件與附近位置縮小範圍；對沒有可靠座標的資料，則以目錄與行政區摘要呈現，而非假裝其位置精確。

目前整合的公共設施資料約有 16,956 筆，涵蓋如垃圾桶、廁所、飲水設施、回收據點、停車與充電服務、公共衛生與都市自然等多種情境。另有獨立的公立學校校園開放資料模組，收錄 224 所學校的原始開放時間文字。

這種設計適合把「我想找一個可用的公共服務」與「我需要了解某區域資源分布」放在同一個產品中，但不把靜態公開資料誤導成即時服務承諾。

## 可以支持的決策

### 生活情境的選擇與規劃

對一般使用者而言，最直接的價值是縮短找尋公共服務的時間。例如：

- 外出前先找附近的公廁、親子廁所、飲水設施或垃圾桶。
- 騎乘電動機車或開車時，以行政區、服務類型與地址資訊規劃補給或停放的備選地點。
- 查詢回收、舊衣回收、定時收運與大型廢棄物等不同服務的官方資訊，先確認哪一類管道較符合需求。
- 依學校、行政區、偏好日與時段查詢校園開放資訊，再向校方確認實際進出與預約規則。

這裡的決策重點是「縮小查詢範圍、建立確認清單」，而不是直接替使用者下結論。介面會保留來源欄位與提示文字，讓使用者知道哪些資訊可以參考、哪些仍需要向現場或主管機關確認。

### 資源盤點與服務缺口討論

行政區分布、類型統計與可篩選的清單，適合用於初步盤點：某區有哪些設施類別、資料是否集中於特定區域、哪些來源缺少座標或開放資訊。這可協助社區工作者、研究者或公共服務團隊提出下一步問題，例如：

- 某行政區的公開資料是否明顯不足，還是來源尚未提供？
- 某一服務類型是否多為地址型資料，因而不適合用精確地圖導航？
- 哪些資料需要優先補齊座標、聯絡方式或更新日期？

儀表板呈現的是「資料所描述的分布」，不是設施供給量、服務品質或使用需求的完整證明。因此它適合探索與討論，不宜直接用來做經費分配、績效評比或安全判定。

### 資料治理與來源溝通

每個轉換流程都會保留原始欄位，並產生缺漏值、重複列、無效座標與座標離群值等品質資訊。這讓資料維護不只是匯入成功或失敗，而能回答更具體的問題：哪個來源的問題最多、問題屬於格式還是內容、是否應回報給資料提供單位。

學校場地模組是很好的例子：來源只提供校園開放時間，沒有場地類型、電話、地址、座標、價格或預約連結。因此系統只把來源文字中明確出現的運動關鍵字標示為「偵測結果」，並把多數紀錄歸為「請向學校確認」。這不是功能不足，而是避免把資料缺口包裝成事實。

## 特別適合的使用場景

| 場景 | 儀表板的角色 | 使用時應注意 |
| --- | --- | --- |
| 市民出行與日常需求 | 找到可進一步確認的公共服務候選點 | 營運時間、供應量與現場狀態可能變動 |
| 社區盤點與倡議 | 比較行政區與設施類型的公開資料分布 | 不可把資料筆數直接當作服務品質或需求量 |
| 資料產品原型 | 驗證不同資料來源能否以同一套查詢模式服務使用者 | 需先界定每種資料的精確度與可宣稱範圍 |
| 公開資料品質檢視 | 找出缺座標、重複、格式不一致與來源更新問題 | 應回到資料提供者確認原始意義 |
| 校園開放資訊查詢 | 依行政區與時段建立詢問校方的候選清單 | 開放校園不等於特定場地可使用或可預約 |

相對不適合的情境包括：需要即時空位、即時營業狀態、精確導航至無座標地點、法律邊界判定、醫療建議，或以單一資料來源做高風險決策。這些需求需要更即時、具責任歸屬且可追溯的資料服務。

## 資料量與效能：遇到的問題與處理方式

### 問題一：大量標記會讓地圖失去可用性

當多個圖層同時開啟時，資料量接近 17,000 筆。若直接為每筆資料建立 Leaflet marker，不只初次渲染變慢，手機上的縮放、拖曳與點擊也會變得不穩定。這是地圖元件數量與 DOM／圖層更新成本造成的瓶頸，不是單純把資料下載得更快就能解決。

採用的做法是「廣域清單優先，縮小範圍後再顯示標記」：

1. 預設清單先顯示有限筆數，避免一次建立過長的卡片列表。
2. 多圖層或過大的結果集不繪製個別 marker，改由清單、篩選器與行政區摘要協助探索。
3. 只有在使用者選定單一類型、行政區、關鍵字或附近搜尋，且有效座標數不超過 500 筆時，才呈現精確 marker。
4. 需要繪製的 marker 會先渲染 240 筆，再以每批 320 筆的方式透過瀏覽器動畫幀逐步加入，讓互動不被長任務完全阻塞。

這個方法的優點是沒有增加額外地圖叢集套件，使用者也不會在密集畫面中面對難以點選的圖釘海；代價是廣域視圖不再是「完整地圖」，使用者必須先篩選。對以查找個別服務為主的行動使用情境，這是較合理的取捨。

若產品轉為以空間分析為主要工作，可改採以下方案：

- **Marker clustering**：適合使用者需要在廣域地圖上感受密度；代價是要處理叢集展開、群組含義與額外依賴。
- **Canvas 或 WebGL 圖層**：適合數萬到數十萬個點的純視覺化；代價是互動、無障礙與每個點的詳細 popup 實作較複雜。
- **向量圖磚或伺服器端空間查詢**：適合資料持續成長、需要多條件地理查詢或即時更新的服務；代價是引入後端、資料庫與部署維運。

### 問題二：資料來源格式與可信度不一致

公開資料可能是 UTF-8、UTF-8-SIG、Big5 或 CP950 CSV，也可能有不同欄名、空白值、地址但無座標、錯誤座標或文字型時間欄位。若直接在前端讀取並假設格式一致，錯誤會散落在各個元件中，且難以追查。

處理方式是把資料清理放在建置前的轉換腳本：先以字串保留原值，再針對每種來源做解碼、欄位正規化、座標範圍驗證、分類與品質報告，最後輸出前端可直接載入的靜態 JSON。這使前端專注在篩選與呈現，也讓轉換規則可被單元測試覆蓋。

取捨是資料不會在使用者開啟頁面時自動反映政府網站的最新內容，更新要由重新下載與轉換流程觸發。對不需要即時狀態、重視可部署性與低成本維護的公共資訊產品而言，靜態快照是合理選擇；若未來需要每日更新、來源版本追溯或多使用者協作，則可改為排程擷取、物件儲存與後端 API。

### 問題三：沒有座標時，不能用看似便利的方式補出答案

許多來源只有地址、學校名稱或行政區，沒有官方座標。自動地理編碼雖能快速補點，卻可能把校門、道路、行政區中心或同名地點誤當成正式位置；對使用者來說，錯誤的精確圖釘往往比沒有圖釘更具誤導性。

因此系統採取分級呈現：有通過範圍驗證的 WGS84 座標才畫精確 marker；地址型資料顯示為可搜尋目錄與行政區摘要；學校場地資料維持目錄優先，不自動以校名推導座標。這保留資料的可用性，同時明確標示精確度界線。

未來若取得可依「機關代碼」精確對應的官方學校位置資料，可在保留來源與更新日期的前提下加入座標。若只能取得名稱相似的資料，則應先建立人工審核流程，而非直接採用模糊比對。

### 問題四：篩選功能容易把「相關」誤說成「已證實」

關鍵字檢索在探索資料時很有效，但不能替代結構化事實。以學校運動場地為例，來源文字只要沒有明確寫出「匹克球」，就不能因為有羽球、網球或多功能場地而把它列為匹克球場。校園開放也不代表可預約、場地有空、免費或符合比賽規格。

系統因此區分原始來源、由關鍵字偵測的結果、可驗證的官方預約資訊與未知狀態。這種保守做法會降低看起來「資料很完整」的效果，但能維持產品可信度，也讓後續資料增補時有明確的欄位與證據規則。

## 架構選擇的理由

前端使用 Vite、React、TypeScript 與 Leaflet，資料以本機 JSON 靜態提供，並透過 PWA service worker 快取。這組合的優勢是：

- 無需帳號、資料庫、後端或付費地圖 API，即可部署到靜態託管平台。
- TypeScript 的資料模型把不同設施來源的共同欄位與特定欄位分開，減少在 UI 中猜測資料形狀的機會。
- React 的記憶化篩選與延後更新，搭配限制清單與 marker 的策略，使中型公開資料集在行動裝置上仍可操作。
- service worker 讓重複造訪可優先使用本機快取，但部署時以版本化快取更新靜態資料。

它的邊界同樣明確：靜態架構不適合即時可用量、即時空位、複雜權限、個人化收藏同步或大規模空間分析。這些需求一旦成為產品核心，就應重新評估是否加入 API、資料庫、地理空間索引與觀測機制，而不是在前端繼續堆疊例外規則。

## 可持續演進的方向

1. 為每個來源顯示資料日期、更新頻率與欄位覆蓋率，讓使用者更容易判斷是否需要再確認。
2. 建立來源差異報告，追蹤每次更新新增、刪除與座標變動的紀錄。
3. 對資料提供單位回饋高價值缺欄位，例如官方座標、預約連結、聯絡方式與機關代碼。
4. 當有可靠的需求或使用量資料後，再評估以區域服務缺口、步行可達性或時段重疊等分析功能輔助規劃。

這些方向的共同原則是：先把資料的來源、精確度與限制說清楚，再提高自動化與決策程度。對公共服務資訊而言，可信的「不知道」通常比未經證實的「可以」更有價值。
