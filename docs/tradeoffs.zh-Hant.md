# 取捨決策紀錄

[English](tradeoffs.en.md) | [繁體中文](tradeoffs.zh-Hant.md)

2026-10-16 依保留快照與目前程式核對；模組邊界詳見[系統設計](system-design.zh-Hant.md)。

## 靜態 App，而不是後端

決策：將所有設施資料放在 `public/data/` 底下作為靜態 JSON。

原因：資料集都是公開、仍足以在前端篩選、且此產品目前只需要讀取。靜態 hosting 可降低維運成本，不需要 API key，也更容易部署到 Vercel 或 GitHub Pages。

拒絕方案：後端 API 或 CMS。它會增加 hosting、驗證與維護負擔，但沒有解決目前的使用者問題。

## 通用 Facility 模型

決策：從只支援清潔箱的資料模型改為含有明確 `type` 的 `Facility`。

原因：共用地圖的 22 種設施有不同語意與來源欄位。明確型別可維持標籤、提醒與篩選的一致性；獨立儀表板保留專屬契約，不把每個分析需求都塞進同一模型。

拒絕方案：把所有便利設施硬塞進舊的 bin model。這會增加將狗便袋箱或公廁誤稱為垃圾桶的風險。

## 保留座標疑似異常列

決策：超出台北市寬鬆 bounding box 的座標會保留，標記 `isCoordinateOutlier: true`，並記錄在 `conversion-report.json`。

原因：可疑座標仍可能有人工查核價值，而且靜默刪除會隱藏資料品質問題。

拒絕方案：刪除所有超出範圍的列。這會讓資料看起來更乾淨，但可稽核性較差。

## OpenStreetMap + Leaflet，而不是 Google Maps API

決策：使用 Leaflet 搭配 OpenStreetMap 圖磚。

原因：不需要 API key，對公共設施查找已足夠，也讓任何人都能部署此專案。

拒絕方案：以 Google Maps embed/API 作為主地圖。App 仍提供 Google Maps 開啟連結，但若主地圖使用 Google Maps，會引入 key 管理與計費風險。

## 前端定位與距離計算

決策：在瀏覽器端用 Haversine 公式計算距離。

原因：使用者位置不需要離開裝置，而且目前資料量足以在本機排序。

拒絕方案：後端最近設施查詢。這會增加隱私與基礎設施成本，但目前沒有明確收益。

## Marker Cap，而不是 Marker Clustering

決策：使用 emoji `divIcon` markers，但當目前結果超過 marker cap 時不渲染設施 markers。

原因：保留的合併資料為 16,956 筆，全部顯示會過度擁擠。共用地圖初始不選類型，選取另一類型會取代前一選取；單一類型且有效座標不超過 500 筆，或附近結果，才顯示精確標記。地址型行政區摘要不代表設施精確位置。

取捨：使用者預設不會看到所有 markers。若產品需要低 zoom 瀏覽全部 markers，下一步再加入 marker clustering。

## 限制預設列表渲染

決策：預設列表只渲染前 80 筆，並顯示提示讓使用者用搜尋或篩選縮小範圍。

原因：一次渲染保留的 16,956 筆不利掃描。搜尋、行政區、來源專屬條件及附近功能同時降低渲染與認知負擔；獨立目錄另有自己的分頁／上限。

取捨：列表與地圖都不保證一次呈現全部符合紀錄，但符合總數仍可見。若需完整瀏覽，可評估分頁／虛擬清單；若需低縮放密度探索，再評估叢集或 Canvas／WebGL，並補足互動與無障礙設計。

## Service Worker 策略

決策：導覽、`/assets/` 與 `/data/bin-policy/` 使用 network-first；其他 `/data/`、圖示及 manifest 使用 cache-first。

原因：如果 app shell 使用 cache-first，使用者可能在部署後仍被舊版 `index.html` 卡住。Network-first 能維持部署更新，同時保留離線 fallback。

取捨：第一次 navigation 會優先使用網路，因此完整離線能力需要使用者先開過此 app。

政策資料使用後才快取，不隨一般地圖預先下載；離線分析須先成功開啟對應模式。外部圖磚不由此 worker 快取；一般資料更新須管理快取版本。建置後以 `npm run test:policy-preview` 驗證 production 行為。

## 明示政策權重，而不是不透明總分

決策：保留交通覆蓋模式 A，另提供模式 B 的固定類別母體計分、可編輯版本化權重、類別貢獻與同輸入敏感度。

原因：原始公車點數可能壓過小類別；類別正規化讓優先取向可被討論，不代表客觀正確。觀光／商圈缺漏保留不可用、不轉配權重；原始新增量與加權分數單位不同。

取捨：小類別可能有較大影響，貪婪法也不保證全域最佳。實務採用前須審查完整性、權重、識別去重、步行與現勘條件。取得可靠使用量與清運成本後，可另評需求／成本模型，不能把參考點改稱服務人數。詳見 [v1.2 方法](bin-policy-v1.2-methodology.zh-Hant.md)。

## 先留證據，再採用新資料

決策：保留原始位元組、雜湊、不同日期、對帳，以及分離的只讀監測／審查發布。

原因：下載成功、雜湊不變或技術驗證通過，不代表服務仍有效或已獲來源採用授權。2021 公車基線仍明示保留，新來源另作比較。

取捨：人工審查有成本，也可能延遲更新；只有在來源身分、排除規則、責任與回復證據可稽核時才擴大自動化。觀光來源受阻仍是實際監測失敗，不是成功取得空資料。
